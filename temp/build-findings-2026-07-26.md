## 失败 1：starter-elasticsearch/example-otel -- 缺 ctx 参数（go-spring 自身代码 bug）✅ 已修复

> **状态：已修复（2026-07-26）。** `example-otel/main.go` 第 145、195 行补上 `ctx` 参数，`go build` 通过（exit=0）。

**现象**
```
./main.go:145:45: not enough arguments in call to StarterElasticsearch.HealthCheck
```

**根因**
- starter 定义的函数签名（`starter/experimental/starter-elasticsearch/starter.go:96`）：
  ```go
  func HealthCheck(ctx context.Context, client *elasticsearch.Client) error
  ```
  是包级自由函数，需要 2 个参数 `(ctx, client)`。
- example-otel 的调用（`example-otel/main.go:145` 和 `:195`）只传了 1 个：
  ```go
  if err := StarterElasticsearch.HealthCheck(s.ES); err != nil {      // 缺 ctx
  ```
- 对照：plain `example/example.go:139` 写法正确：`StarterElasticsearch.HealthCheck(ctx, s.ES)`。

**修复方案**
- 在 `example-otel/main.go` 第 145、195 行补上 `ctx`：
  ```go
  StarterElasticsearch.HealthCheck(ctx, s.ES)
  StarterElasticsearch.HealthCheck(ctx, s.DiscES)
  ```
- 风险：无。机械修复，与已通过的 plain example 对齐。
- **推荐：直接改，2 行。**

## 失败 2：gs-http-gen/examples/go -- 生成器 bug（Email(Email)）

**现象**
```
proto/manager.go:598:19: cannot use Email (variable of type func(string) (bool, error)) as string value in argument to Email
```

**根因**
- 生成代码 `examples/go/proto/manager.go:598`（文件头 `// Code generated by gs-http-gen compiler. DO NOT EDIT.`）：
  ```go
  func (x *ContactInfo) Validate() error {
      ok, err := Email(Email)   // 第一个 Email 是校验函数，第二个 Email 应是字段 x.Email
  ```
- `examples/go/proto/validate.go:7` 定义了同名校验变量：
  ```go
  var Email = func(string) (bool, error) { return true, nil }
  ```
- 结构体字段 `ContactInfo.Email string`（manager.go:473）。生成的 `Email(Email)` 里第二个 `Email` 本应是 `x.Email`（string），却写成了裸 `Email`，解析成了那个 func 变量 -> 类型不匹配。
- 生成器 bug 在 `gs/gs-http-gen/gen/generator/golang/type.go`：
  - 第 213 行 `dollar := "x." + fieldName`（`$` 占位符的正确展开，带 `x.` 前缀）；
  - 但第 284 行 `compileBoolExpr(fieldName, x.Left)` 传进去的是 `fieldName` 而非 `dollar`；
  - `$` 分支（约 322 行）返回了 `fieldName`（"Email"），漏了 `x.` 前缀。

**修复方案**
- A. **修生成器**（治本）：改 `type.go` 让 `$` 占位符输出 `x.<fieldName>`，然后重新生成 manager.go。需运行 gs-http-gen 重生成。
- B. **直接改生成产物**（治标）：manager.go:598 `Email(Email)` -> `Email(x.Email)`。但文件标注 DO NOT EDIT，下次重生成会还原。
- 备注：`gs/gs-http-gen` 在 `scripts/check-go-modules.sh` 里被显式排除（`! -path './gs/gs-http-gen/*'`），不进 CI；且 `go-spring.org/gs-http-gen` 未发布，其 replace 必须保留。
- **推荐：A（修生成器），否则重生成会复现。** 若赶时间可先 B 临时通过。

## 失败 3：goframe 4 个模块 -- 上游版本不兼容（最难，需裁决）

**涉及模块**
- `contrib/goframe/http`
- `starter/experimental/starter-goframe`
- `starter/experimental/starter-goframe/http/example`
- `starter/experimental/starter-goframe/http/example-otel`

**现象**（4 个相同）
```
gogf/gf/contrib/metric/otelmetric/v2@v2.10.2/otelmetric_provider.go:94:14:
  invalid operation: cannot call runtime.Version (untyped string constant "0.68.0"):
  untyped string is not a function
```

**根因**
- goframe contrib `otelmetric v2.10.2`（**已是最新版**，无更高版本可升）的 `otelmetric_provider.go:12` 导入：
  ```go
  import "go.opentelemetry.io/contrib/instrumentation/runtime"
  ```
  第 94 行调用 `runtime.Version()` 当函数用：
  ```go
  Version: runtime.Version(),
  ```
- otel-runtime 的 `Version` 在版本间改了类型：
  - **v0.63.0**：`func Version() string`（可调用）-- goframe contrib v2.10.2 的 go.mod 要求的就是 v0.63.0。
  - **v0.68.0**：`const Version = "0.68.0"`（常量，不可调用）。
- workspace 的 MVS 把 otel-runtime 选到了 **v0.68.0**（因为 `starter-otel` 和 `starter-goframe` 的 go.mod 都记录了 v0.68.0），导致 goframe 调 `runtime.Version()` 报错。
- 即：**goframe contrib 最新版尚未适配 otel-runtime v0.68.0 的 API 变更**，纯上游不兼容，与 replace 无关，replace 也救不了。

**修复方案（需你裁决）**
- **A. 接受这 4 个模块暂不通过**：记录为已知上游问题，其余 218 模块全过。等 goframe 发新版。
- **B. workspace 全局把 otel-runtime 钉到 v0.63.0**：在 go.work 加 `replace ... v0.68.0 => v0.63.0`。goframe 能过，但**风险**：要验证 starter-otel 在 v0.63.0 下仍能编译/运行（它声明用 v0.68.0），可能损失 v0.68 新特性或编译失败。
- **C. 把 4 个 goframe 模块排除出 go.work 的 use**：单独 GOWORK=off 构建。但 starter-goframe 的 go.mod 间接已记录 v0.68.0，单独构建仍会选 v0.68.0，需配合 `go mod tidy` 降版本 + 补 replace，回到旧的独立构建模式，与你"尽量不用 replace / 全量 workspace"的方向相悖。
- **推荐：A**（最干净，上游问题不该由本项目兜底）；若 goframe 是刚需则 B，但需先验证 starter-otel 兼容性。

## 编译慢的问题与解法（含实测）

### 现象与实测数据

| 方式 | 范围 | 耗时 | 结果 |
|---|---|---|---|
| 顺序 `cd 各模块 && go build ./...` | 222 模块 | **~8–10 分钟** | 216 通过 / 6 失败 |
| **并行 `xargs -P 8`**（已验证） | 216 模块（排除 6 个已知失败） | **2 分 08 秒**（12:51:17 -> 12:53:25） | **216 通过 / 0 失败** |

并行约 **4 倍加速**，且 0 失败（log 版本修复 + replace 删除都站得住）。

### 慢的根因（两层）

1. **otel 栈本身大**：`*/example-otel` 通过 `starter-otel` 引入整套 OpenTelemetry -- SDK + otlpmetric/otlptrace 各类 exporter（grpc+http）+ Prometheus client + gRPC + genproto，**数百个包**。首次编译 CPU 密集、要数分钟。Go build cache 命中后重复构建才快。
2. **每次 `go build` 调用都要加载 222 模块的 workspace 图**：当前验证是 per-module 独立调用，222 次调用每次都重新加载整个 workspace 图，这是固定开销，与编译量无关。

### 慢的具体范围

- 全部 `*/example-otel`（约 37 个）+ `starter/experimental/starter-otel` 本身：都拉 otel 整栈，最重。
- `contrib/goframe/http`、`starter/experimental/starter-goframe`、`starter-goframe/http/*`：goframe 框架本身很大 + otel 栈，最慢的一档（且当前因上游不兼容编译失败，见失败 3）。
- `contrib/dubbo-go/*`、`starter/experimental/starter-dubbo/*`：dubbo-go 栈较重。

### 解法（按收益排序）

**1. 并行构建（已验证有效，推荐）**
用 `xargs -P N` 并行跑各模块 `go build ./...`，多核重叠。Go build cache 支持并发访问，otel 栈谁先编谁写 cache，其余命中。
```bash
# /tmp/build_one.sh：入参模块目录，go build 后打印 PASS/FAIL
cat /tmp/modules_to_build.txt | xargs -P 8 -I{} /tmp/build_one.sh {}
```
实测 8 核 216 模块 2m08s。`-P` 取 `sysctl -n hw.ncpu`。

**2. 从 repo 根单次 `go build ./...`（更快，但有坑）**
一次调用覆盖所有模块，otel 栈只编译一次 + 只加载一次 workspace 图 + 内部并行，理论上最快。但会暴露被 per-module workspace 覆盖掩盖的版本错误：从根构建走全图 MVS，挑出不存在的版本就挂。实测暴露了 `starter-transaction-tcc/example-otel` 误写 `go-spring.org/log v1.3.4`（应为 v0.1.4，**已修**）。修掉这类错误后此法可用，还能顺手揪出更多被 replace 掩盖的版本问题。

**3. 排除已知失败/无关模块**
跑验证时排除 5 个已知 broken（goframe×4 上游不兼容 + gs-http-gen），既省时（goframe 最慢）又给干净结果。temp/ 一贯排除。（elasticsearch/example-otel 已修复，不再排除。）

**4. 预热 build cache**
先单独编 `starter-otel`，把 otel 栈编进 cache，后续 example-otel 全命中。

**5. 只 build 不 test**
`scripts/check-go-modules.sh` 现在对每模块跑 `go test`（含测试编译，更慢）。只验编译用 `go build` 更轻。

**6. 减小 otel 栈（治本，改动大）**
`starter-otel` 现在导入全部 exporter，若多数 example 只用其一，可拆分按需导入，缩减编译图。

### 当前验证脚本的局限
- `scripts/check-go-modules.sh` 顺序跑 `go test`，重模块非常慢；建议改并行 + 只 build。
- `gs/gs-http-gen/*` 在该脚本里被显式排除（`! -path './gs/gs-http-gen/*'`），不进 CI（所以失败 2 不会被 CI 捕获）。
